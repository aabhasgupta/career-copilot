# Decision Log

What we chose, why, and what we rejected. New sessions: read this before proposing alternatives to any of these.

## D1: Assisted apply, never auto-submit
**Chosen**: the agent discovers, scores, and prepares everything; the human reviews and clicks submit.
**Rejected**: zero-touch auto-submission (AIHawk/LazyApply style).
**Why**: LinkedIn and similar platforms detect and ban automation on accounts; mass-generated applications have measurably worse response rates; and quality-of-tailoring beats volume. Also a portfolio consideration: "scores fit and tailors applications" is a strong story, "evades anti-bot detection" is a liability. The local Playwright prefill in Phase 3 stays inside this line: public ATS forms, user's own machine, human always submits.

## D2: No LinkedIn/Glassdoor/Indeed scraping
**Chosen**: aggregator APIs (Adzuna, optionally JSearch which indexes LinkedIn/Indeed/Glassdoor postings) plus public ATS APIs.
**Rejected**: logging into job boards and scraping listings.
**Why**: ToS/ban risk on the user's real accounts, high maintenance (DOM changes, CAPTCHAs), and coverage overlap is high anyway since most LinkedIn postings are cross-posts of company ATS boards. LinkedIn-exclusive feed posts are a known, accepted gap; the user can still Easy Apply manually and track it here.

## D3: No hand-curated company list; watchlist builds itself
**Chosen**: broad aggregator search is the front door; when a result's apply URL reveals a Greenhouse/Lever/Ashby slug, the company auto-joins a watchlist whose boards are polled directly thereafter.
**Why**: the user explicitly does not want to be restricted to a fixed company list. ATS boards give cleaner JDs and earlier postings than aggregators, so the system gets faster and richer the longer it runs.
**Update (2026-07-19, Phase 1 build)**: the detection code is implemented (`discovery/ats.py`) and correct, but in practice it finds nothing - Adzuna's apply link always proxies through `adzuna.com` rather than the employer's own posting, and live JSearch sampling never returned a direct apply link either (`job_apply_is_direct` was `false` on every result checked). The self-building watchlist as originally scoped needs real ATS URLs to key off of, which these two aggregators don't expose.
**Resolution (same day)**: the mechanism was inverted rather than dropped - instead of sniffing apply URLs for an ATS domain, each newly discovered company's *name* is probed against the three public ATS APIs (`discovery/ats_resolver.py`; free, unauthenticated). Matches are watchlisted and their boards polled on every discover run (`discovery/ats_boards.py`): postings matching a known job upgrade it in place to the direct employer apply link and full JD text; postings matching the profile's search titles are added as new jobs. Guardrails learned from live false positives: loose first-word slug guesses are only trusted on Greenhouse (the one ATS that echoes the company name back for verification - Capital One matched an unrelated Lever board named "capital" without this), title matching for upgrades is exact-only, and same-title-multiple-location postings are only linked when the location disambiguates. Direct-link coverage will never be 100% - Workday/iCIMS/in-house ATSes have no public API - and the aggregator link remains the fallback.

## D4: Single-user architecture, generic through configuration
**Chosen**: all personal data in `profile.yaml` + resume file; code reads config, never hardcodes the user.
**Rejected**: multi-user product infra (auth, hosting, multi-tenant DB).
**Why**: multi-tenancy roughly doubles build cost while teaching little about agents. Clone-and-configure is the norm for strong open-source projects of this kind. The profile-config boundary is the exact seam to refactor at if this ever becomes a product.

## D5: SQLite as source of truth from day one
**Chosen**: every phase writes to `copilot.db`; CLI, digest emails, and any future dashboard are read layers.
**Why**: no migration/backfill when the dashboard phase arrives; months of history make the visualizations worth having; timestamps (`posted_at`, `applied_at`, `received_at`) let the Phase 5 scorer learn from the user's own outcomes.

## D6: Microsoft Graph for email, behind a provider interface
**Chosen**: user's primary inbox is Hotmail/Outlook.com, so Outlook via Microsoft Graph (MSAL device-code flow) is the primary `EmailProvider`; Gmail is the second implementation for genericity. Provider selected in `profile.yaml`.
**Superseded**: the original plan assumed Gmail. Changed 2026-07-18 when the user clarified their primary account.
**Note**: Outlook folders + categories fulfill the "organize into a folder/tag" requirement.

## D7: Email sending in Phase 2, inbox monitoring in Phase 4
**Chosen**: Graph auth + `sendMail` (digest, alerts) lands with scoring; reading/classification lands after applying starts.
**Why**: email is the only passive channel, so digests are valuable as soon as discovery+scoring work; but there is nothing to monitor until applications exist, and building the classifier before real reply emails exist means building against imagined data.

## D8: launchd, not cron; laptop does not need to stay on
**Chosen**: launchd-scheduled CLI runs, managed by a `copilot schedule` command group.
**Why**: cron silently skips jobs missed during sleep; launchd fires them on wake. The system is poll-based, so missed runs mean delayed data, never lost data. Off-machine scheduling (GitHub Actions / small VM) is the documented escape hatch if closed-laptop latency ever matters.

## D9: Python 3.12 + uv
**Chosen**: Python with uv, SQLAlchemy, Typer, httpx, Anthropic SDK.
**Rejected**: TypeScript/Node (equally capable, better only if this were web-first).
**Why**: first-class libraries for every integration on the roadmap, lingua franca of agent engineering (learning transfers), and the CSV/data work (H1B disclosure files, dedupe, scoring) is bread-and-butter Python.

## D10: Visa status is a first-class field, unknowns are kept
**Chosen**: per-job `visa_signal` (explicit_yes / explicit_no / unknown) and per-company sponsorship evidence from public H1B data (USCIS H-1B Employer Data Hub, DOL LCA disclosures). Jobs with no visa information are still surfaced and tracked as unknown, never filtered out.
**Why**: user needs H1B transfer; sponsorship-unknown jobs are still worth applying to, and no existing market tool (Teal, Simplify, Huntr) tracks this at all - it is a genuine differentiator.

## D11: Local web dashboard is the primary human surface (decided 2026-07-19)
**Chosen**: promote the "later / optional" local web dashboard into Phase 3 as the main way the user reviews jobs and tracks applications: a localhost page over the same SQLite DB showing scored jobs (fit, salary, location, visa signal, apply link) with a mark-applied action. The CLI keeps the machine-facing commands (discover, score, schedule).
**Rejected**: CLI-only application tracking (`copilot mark applied <id>` one row at a time).
**Why**: the review loop is browse-heavy - dozens of jobs, open link, come back, tick off - which a table UI handles far better than per-ID CLI commands. Fits D5 exactly: the DB stays the source of truth and the dashboard is just another read/write layer. Manual marking is expected to become the fallback anyway once Phase 4 lands: ATS confirmation emails ("we received your application") let the email agent auto-mark applications with the correct timestamp, and rejections/interview invites auto-update state the same way.
**Update (2026-07-19, same day)**: the first slice shipped early at the user's request - `copilot dashboard` serves a localhost preferences editor (FastAPI) for profile.yaml's search section, so tuning titles/filters/preferences is a form instead of a YAML edit, encouraging frequent refinement. It writes through the same comment-preserving ruamel helpers the CLI uses and validates the whole profile before saving (invalid input writes nothing). The jobs table/mark-applied views land with Phase 3 proper on this same app.

## D12: Preferences reorder, filters drop (decided 2026-07-19)
**Chosen**: two distinct mechanisms in `profile.yaml`. Filters (`dealbreakers`, `min_salary`) remove jobs from view - and per D10, `min_salary` only drops jobs whose *known* salary is below the floor; unknown-salary jobs always stay. Preferences (`search.location_preference`, an ordered list) never hide anything: they sort listings so the best-matching jobs are at the top, with unmatched jobs last but visible. Entry forms: `remote`, `within <N> miles of <place>` (haversine over job coordinates - Adzuna provides them, others are geocoded once via Nominatim and cached), or plain text matched against the location (with a city-part fallback, since sources format the same place differently).
**Rejected**: folding location preference into the Phase 2 LLM fit score alone.
**Why**: the user's goal is "don't make me spend time choosing what to apply to." Deterministic preference ordering is transparent (the Pref column shows exactly why a job ranked where it did), free (no LLM tokens), and instant. The Phase 2 fit score will layer on top - fit becomes the primary sort with preference tier as input/tiebreak - but location ordering shouldn't cost tokens or be non-reproducible.
**Update (2026-07-19, same day)**: at the user's request, `min_salary` was promoted from view-time filter to a full hard filter: jobs whose known salary is below the floor are now dropped at discovery (never stored) as well as hidden. The D10 rule is unchanged - unknown salary never trips the floor. Rule changes take effect retroactively via `copilot jobs prune`, which re-applies the current dealbreakers + floor to already-stored jobs with zero API calls: everything ever discovered lives in the DB, so the DB itself is the cache to re-derive from (raw aggregator responses are deliberately not kept separately). Jobs with an application on file are never pruned.

## D13: Industry preference via one-time LLM company classification (decided 2026-07-19)
**Chosen**: `search.industry_preference` follows the D12 pattern (ordered list, reorders listings, never hides). Since no discovery API reports a company's industry, each company is classified once by Claude into a fixed vocabulary (banking, fintech, insurance, healthcare, tech, consulting, staffing, government, retail, manufacturing, energy, education, media, nonprofit, other) and the label is stored on the companies table forever. One batched structured-output call per discover run, covering only never-before-seen companies; zero calls when nothing is new; classification failure degrades gracefully (jobs still listed, industry unmatched).
**Rejected**: keyword-matching JD text against industry terms (a bank's JD saying "technology" would misfire constantly), and re-asking the LLM at list time (cost per view, non-reproducible ordering).
**Why**: user knows which industries fit them (banking/fintech first, then tech, then consulting - deep financial-services ML background). Classify-once-then-deterministic keeps read-time ordering transparent and free, same reasoning as D12. The fixed vocabulary makes preference entries exact-match instead of fuzzy. First live run: 76 companies classified accurately (JPMorgan/Citi/Capital One/Synchrony -> banking, Affirm/Blend -> fintech, Bain/Booz Allen -> consulting) and, usefully, exposed that 21 of 76 discovered companies are staffing agencies.

## D14: Dealbreakers are plain English, compiled once (decided 2026-07-20)
**Chosen**: `search.dealbreakers` entries are natural language ("don't give me jobs based in Alabama", "no clearance jobs", "nothing at Meta"). Claude compiles the list once into structured matchers against specific job fields (text / location / company), cached in data/dealbreaker_rules.json until the list or model changes; the compiled rules are then applied deterministically and free to every discovered job and to `jobs prune`. Compilation failure degrades to the old raw-substring behavior rather than blocking discovery. Same compile-once-then-deterministic pattern as D13.
**Rejected**: raw substring matching as the user-facing contract (the user can't know what strings JDs actually contain - "based in Alabama" would never match anything), and LLM-evaluating every job against the rules at discovery time (cost per job, non-reproducible filtering).
**Why**: the user shouldn't need to reverse-engineer JD phrasing to express an intent. Compilation also generalizes intent better than any literal string: in live testing, "clearance required" compiled to seven patterns including "polygraph" and "top secret clearance", and the Alabama rule targeted the location field with both "alabama" and ", al" - none of which substring matching on the user's original words would catch.

## D15: Removed the separate remote yes/no preference field (decided 2026-07-20)
**Chosen**: `search.remote` (remote/hybrid/onsite/any) is gone. Remote appetite is expressed through `location_preference` ("remote" first = prefer it) or a dealbreaker ("no fully onsite jobs" = require it, via D14).
**Why**: the user flagged the ambiguity - two fields both claiming to express location/remote desire, and the `remote` field was in fact dead config that nothing read. One knob per intent: preferences order, dealbreakers drop. Pydantic ignores the leftover key in existing profile.yaml files, so removal is non-breaking.

## D16: Company preference seeds the watchlist (decided 2026-07-20)
**Chosen**: `search.company_preference` is a third preference dimension (D12 pattern: ordered list, reorders listings, never hides; whole-word matching so "Stripe" doesn't catch "Stripes Group"). Beyond ranking, preferred companies are seeded into the companies table on every discover run, so their public ATS boards get probed and polled like any discovered company - their matching postings arrive with first-party apply links without waiting for an aggregator to index them. Additive only: never restricts what else is discovered, so D3's no-hand-curated-list principle stands.
**Why**: "I'd love to work at X" is a real preference the aggregator net can't express, and it makes the watchlist proactive for exactly the companies where being early matters most to the user. First live run: Stripe resolved to greenhouse/stripe, classified fintech, and 5 matching US roles landed with direct stripe.com apply links - including an AI Engineer posting in Chicago.

## D17: Per-dimension sub-scores are captured but not shown in `jobs list`; fit_score is holistic, not their average (decided 2026-07-23)
**Chosen**: `copilot score` produces five 0-100 dimension scores (skill match, experience level, domain fit, location fit, visa feasibility) alongside the overall `fit_score`, all in one Claude call. The dimensions are stored as their own columns on `jobs` but only surfaced via `copilot jobs show <id>`, never as extra columns in `jobs list`. The prompt explicitly instructs the model that `fit_score` is its own holistic judgment, not an arithmetic average of the five - a job can score high overall on the strength of skills/experience despite one weak dimension, or vice versa.
**Why**: the user asked for dimension-level detail without wanting `jobs list` cluttered with five more numeric columns on top of Pref/Industry/Salary/Source. Keeping the overall score as the model's own judgment (rather than a derived average) avoids the score feeling less discriminating just because it now has structured parts - and matches how a human would actually weigh conflicting signals rather than mechanically averaging them.

## D18: Sponsorship data (public H1B filings) is never blended into fit_score (decided 2026-07-23)
**Chosen**: `copilot sponsorship-sync` matches companies against the public USCIS H-1B Employer Data Hub (deterministic name normalization, zero LLM cost - same compile-once philosophy as D13/D14 but with no model call at all) and populates `Company.h1b_filing_count` / `sponsorship_evidence` / `sponsorship_status`. This data is surfaced only as separate context in `copilot jobs show <id>`, alongside but never merged into the job's `visa_feasibility_score`, which stays based purely on that job's own JD language.
**Why**: the user pushed back on folding the two together - correctly. The USCIS export is FY2023 (already dated), aggregated at the whole-company level, and a lagging indicator: a company can freeze sponsorship or sponsor for some roles/teams and not others, none of which the filing data would reflect. Blending it into a single 0-100 number would imply a confidence the data doesn't support and conflate "what this specific posting says" (current, role-specific) with "what this company filed in 2023" (dated, company-wide). Keeping them separate is more honest and lets the user weigh both signals themselves.
**Matching caveat worth knowing**: filing data lists legal entity names ("AMAZON COM SERVICES LLC") that often differ from the brand name a job posting uses ("Amazon"). Matching is exact-after-normalization first, then a prefix match - but only for distinctive names (2+ words, or a single word of 6+ characters) to avoid the same false-positive risk already hit once with loose ATS slug matching (D3): short acronym brand names (e.g. "EXL", "CGI") that differ from their legal filer name will often go unmatched by design, favoring precision over recall. Verified live: Amazon (6,126 approved), JPMorgan Chase (1,525), Stripe (64), Capital One (50) all matched correctly; MITRE Corporation correctly stayed `unknown` rather than a wrongly-inferred `no_sponsor` - it genuinely has zero H1B filings in the data, consistent with its defense-adjacent, citizenship-restricted hiring.

## D19: Dashboard's Jobs view is the "unified view", built read-only ahead of Phase 3 (decided 2026-07-23)
**Chosen**: the user asked for a single place to see fit scores, dimension breakdowns, and sponsorship evidence together - something no CLI table can do without becoming unreadable (the CLI already hit that ceiling: Pref/Industry/Fit crowd the terminal at 8+ columns). Rather than build more CLI reporting commands, the existing `copilot dashboard` (D11, previously just the preferences editor) grew a second page: `/jobs` (sortable/filterable table, best-fit-first) and `/jobs/<id>` (full breakdown - reasoning, all 5 dimension scores, sponsorship evidence). Both are read-only: no mark-applied, no application tracking, no packets - that's still Phase 3 scope and needs machinery (tailoring, packet generation) that doesn't exist yet. The ranking logic itself was factored out of `cli.py` into `ranking.rank_jobs()` so the CLI's `jobs list` and the dashboard's `/jobs` can never drift apart on how "best first" is defined.
**Why**: this is exactly the kind of "later/optional" dashboard work the project always intended to build incrementally rather than as one big Phase-3 bang - the preferences editor was pulled forward the same way in D11's update. A visual, scannable view is a materially better fit for browsing dozens of scored jobs than a wall of CLI text, and it's the natural home for the sponsorship/fit "unified view" the user asked for, without overbuilding application-tracking features that would need to be redesigned once Phase 3's tailoring/packet work exists anyway.
**Visa/sponsorship display note**: the Jobs table shows one combined column with the strongest signal winning - an explicit JD statement (specific, current) displays over company-wide filing history (dated, aggregate) - but the detail page always shows both separately in full, preserving D18's separation underneath the surface-level simplification.

## D20: Inbox monitoring - one folder + categories; untracked applications are suggested, never auto-tracked (decided 2026-07-24)
**Chosen**: two linked decisions for Phase 4's `copilot inbox sync`, worked out ahead of building it.
1. **Folder structure**: every job-related email moves into a single "Career Copilot" folder, not per-type subfolders. Type is expressed via Outlook categories (a colored label per message - "Rejection", "Interview Invite", "Recruiter Screen", "OA", "Confirmation"; this is why the Azure app registration requested `MailboxSettings.ReadWrite`, needed to create custom categories). Categories are additive tags on a fixed, one-time event (the email itself never changes), whereas an application's *state* evolves over multiple emails - subfolders would force re-filing messages as state changes; categories don't.
2. **Untracked applications** (a reply about a job you applied to outside Career Copilot - manually, via LinkedIn Easy Apply, or a posting the discovery pipeline never found) are never auto-added to the applications pipeline. `inbox sync` runs a pre-filter first (only sender/subject patterns typical of ATSes/recruiting are even considered, not every inbox email - keeps this both cheap and non-invasive), then tries to correlate against existing `applications`. When a message is confidently job-related but correlation finds nothing, it becomes a pending suggestion - the email is left completely untouched (not moved, not categorized) - until the user confirms. Only on confirmation does copilot create a stub `Company`/`Job`/`Application` (state seeded from what the email itself indicates - e.g. a confirmation email starts it at `applied`) and file the email. Declining leaves everything exactly as it was, as if sync never looked at it.
**Why**: (1) keeps the "database is the source of truth, Outlook is a mirror" principle (D5) intact - the folder/category is a courtesy reflection of the DB record, not a second place state lives; (2) matches D1's "assist, never act unilaterally" - creating a pipeline entry is a bigger deal than filing an email, so it needs explicit confirmation, same reasoning as never auto-sending referral drafts or application packets.
**Schema implication - none needed**: `email_events.application_id` stays a required foreign key; it does *not* need to become nullable. `Job.source` already holds per-channel values (`adzuna`, `jsearch`, `greenhouse`, ...) - an email-inferred stub just adds `source="email"` as another valid value. Every email event still points at a real application; some applications were created by discovery, some were created retroactively from a confirmed email suggestion. Everything downstream (`copilot status`, the dashboard, the state machine) already works uniformly across sources with no special-casing.
**Resolved 2026-07-25 (D25)**: the review queue gets both a CLI flow and a dashboard view - see D25.

## D21: Posting age is a live floor plus a ranking tier, not a one-time discovery-time drop (decided 2026-07-24)
**Chosen**: two additions to `ranking.rank_jobs` and the `jobs list`/dashboard query layer, both keyed off each posting's own `posted_at` (already captured per-source since Phase 1, just never surfaced until this session added `formatting.format_posted()`).
1. **`search.max_posting_age_days`** (default 30) is a query-time floor, re-evaluated against "now" every time `jobs list` or the dashboard's `/jobs` runs - not a filter applied once at `discover` time. A job's age increases every day regardless of whether `discover` re-runs, so a one-time drop (like D14's dealbreakers) would miss postings that go stale while just sitting in the DB. Same "unknown, never dropped" rule as the salary/fit floors (D10): a job with no `posted_at` is always kept, never assumed stale. `--all` (CLI) / a blanked "Max age" field (dashboard) disables it.
2. **`freshness_tier`** in `rank_jobs`: postings within `FRESH_WINDOW_DAYS` (14) group ahead of older ones as a real ranking signal - placed after the staffing downrank and before the location/industry/company preference blend - not merely the pre-existing last-resort tiebreak (which now also switched from `created_at`, when *we* discovered the job, to `posted_at`, when the source says it actually went live).
**Rejected**: a single blended weighted score combining fit + recency into one number - opaque and hard to reason about compared to the existing tier-cascade pattern the ranking already uses for staffing/location/industry/company. Also rejected: hard-dropping stale postings permanently from the DB - the DB is meant to hold everything ever discovered (README); a live query-time floor achieves the same visible effect without destroying data or needing a decision about whether "stale" is reversible.
**Why**: user feedback - "there is no point applying to a job posted 60 days ago" - and a request that recency actually shape the default ordering, not just break ties between otherwise-identical fit scores. 30 days was chosen over 60 based on live data: of 506 stored jobs, 119 (23%) were already over 30 days old and 73 (14%) over 60 - 30 is the more defensible "still worth applying to" line. `fit_score` still dominates the overall ordering (verified live: a 78-fit job posted 10 days ago outranked another 78-fit job posted 15 days ago that had a location-preference match, confirming freshness sits ahead of the preference blend but fit_score is still checked first).

## D22: Dropped Playwright browser prefill; packet is boilerplate + one small per-job addendum, not five sections regenerated per job (decided 2026-07-24)
**Chosen**: two changes to the original Phase 3 sketch, worked out in design discussion before building any of it.
1. **No browser automation.** The plan previously had a second Phase 3 half - Playwright filling standard ATS form fields on the user's machine, stopping for the user to finish custom questions and submit. That's dropped entirely. Phase 3 now ends at "packet generated, content is paste-ready" - actually getting it into the ATS form is either manual copy-paste or via an existing free tool like Simplify, which already solves per-ATS field detection as its whole product.
2. **Packet content is layered, not monolithic.** Most of what a packet contains - contact details, H1B-transfer work-authorization phrasing - is identical across every job and shouldn't be regenerated (or re-spent LLM budget) per posting. Only a small addendum is genuinely job-specific: a short "why this job" blurb (reusing the job's existing `fit_reasoning`) and which resume bullets/skills to foreground for that posting. Custom application-form questions are not drafted at all - the JD text available at packet-generation time isn't the actual apply-form content, so guessing at unseen questions was quietly optimistic rather than useful; the packet says so explicitly instead of inventing plausible answers.
**Rejected**: building a from-scratch browser-automation or Chrome-extension autofill feature. Considered both a Playwright-driven local prefill (closer to the existing Python stack) and a browser extension (closer to how Simplify itself works) - rejected both as a large, ongoing engineering investment (per-ATS DOM quirks, breakage as forms change) to rebuild something free tools already do well, for a single-user project where that effort doesn't showcase anything the rest of Career Copilot is actually about (fit scoring, sponsorship research, tailored reasoning).
**Why**: user pushback in design discussion - "most of the things would be common to all job applications" (correct: sections 1-2 of the original packet sketch were static, not tailored) and "are there tools that are free already like that" (yes - Simplify and similar autofill extensions already solve exactly this). Reusing existing tooling for the mechanical form-filling and keeping Career Copilot focused on the content-generation problem it's uniquely positioned to solve is a better use of build time than re-solving a problem the ecosystem has already solved well.

## D23: Dropped the per-job packet addendum; Phase 3 ships one reusable base packet only (decided 2026-07-24)
**Chosen**: further design discussion (immediately after D22) concluded the per-job addendum from D22 - the one-Claude-call "why this job" blurb and bullet-foregrounding - wasn't worth building yet either. Phase 3 now produces exactly one artifact: `data/packet_base.md` (contact details, H1B-transfer work-authorization Q&A), generated by explicit command/button (`copilot packet base`) and reused unchanged across every job. No per-job file, no per-job LLM call, no `Application.tailored_materials_path` pointing at anything job-specific.
Also clarified along the way: even the "why this job" content from D22's addendum was never a verified answer to a real form question - the JD text available at generation time isn't the actual apply-form content, so it could only ever be prep talking points, not a drafted form answer. That distinction, surfaced during design discussion, made the addendum's value harder to justify as a discrete build item versus something the user can just think through themselves from the job's existing `fit_reasoning` (already visible in `jobs show`/the dashboard).
**Why**: the user's own framing - "why are we still debating on the per-job packet? I think we can completely drop it for now." Accumulating open questions (how literal should bullet rewording be, is the addendum answering a real question or not) about a small, speculative piece was a sign it wasn't earning its complexity yet. Shipping the base packet alone first, then observing whether its absence is actually felt in practice, is a cheaper way to find out than building it speculatively now. Nothing is closed off - a per-job layer can be added back on top of the base packet later if real usage shows it's needed (the base/addendum split from D22 still applies if it comes back).

## D24: Email-derived state changes advance automatically; conflicts with a human-set state are flagged, never silently overwritten (decided 2026-07-24, ahead of building Phase 4)

**Chosen**: once Phase 4's inbox sync exists, it will write to `Application.state` from classified, correlated emails - the same field Phase 3's manual "Queue"/"Mark applied" actions already write to. Two write paths on one field need a rule for when they disagree.
1. **Plain forward progress is automatic, no confirmation needed.** If the correlated email's implied state is consistent with (equal to or further along than) the current state - e.g. DB says `found`/`queued` and a confirmation email arrives, or DB says `applied` and an interview-invite email arrives - `inbox sync` just advances `Application.state`, same as Phase 4 was always meant to work. This is the common case and stays silent/automatic.
2. **A genuine conflict is flagged, not resolved unilaterally.** If the correlated email's implied state contradicts the current state in a way that isn't simple forward progress - most sharply, the email implies the application is further along than a state a human explicitly set - it's surfaced as a flagged discrepancy (same "suggest, don't act" shape as D20's untracked-application suggestions) instead of being written automatically. The user picks one side; nothing gets silently overwritten either direction.
3. **Distinguishing "human-set" from "system-set" requires knowing who set the current state**, which `Application.state` alone (a single mutable column) can't answer. Phase 4 will need a lightweight state-history record - each transition tagged with its source (`manual` vs `email:<event_id>`) - not just the current value. Not built now (Phase 4 hasn't started); recorded here so the schema work doesn't get skipped when that phase begins.

**Rejected**: emails always win (an ATS's automated "we received your application" is real evidence, but so is a deliberate human click, and neither should be able to silently overrule the other - a misclassified or misdirected email is just as plausible as a mistaken click). Also rejected: manual state always wins / email correlation only fires for jobs still at `found` (would defeat the point of Phase 4 catching up state changes - rejections, interview invites - for jobs already marked applied).

**Why**: raised by the user ahead of Phase 4 - "what happens then? what or who will supersede who?" - specifically about accidental reverts, but the real issue is broader: any two independent writers to the same field need a conflict rule, and D1 ("assist, never act unilaterally") already answers it - Copilot doesn't get to unilaterally decide a disagreement between what a human said and what it inferred from an email, it surfaces the disagreement and lets the human resolve it, exactly like D20 already does for untracked applications. Today's Phase 3 has no state-downgrade path at all (`queue()` only advances `found -> queued`, `mark_applied()` only advances forward), so this conflict cannot occur yet - this decision exists so it's already answered when Phase 4 introduces the second writer.

## D25: Resolved Phase 4's two open items - review queue lives in both CLI and dashboard; state-history table built now, ahead of Phase 4 (decided 2026-07-25)

**Chosen**: two decisions closing out the "open" notes left in D20 and D24.
1. **D20's pending-suggestions review queue** (untracked, job-related emails that don't correlate to any tracked application) will get both surfaces: a CLI command (`copilot inbox review` / `confirm <id>` / `decline <id>`) built first since it's simpler and needed regardless, and a dashboard "Suggestions" view added alongside it, following the same click-through pattern as the Jobs tab (D19). Neither replaces the other - CLI for quick/scriptable review, dashboard for browsing evidence with more context.
2. **D24's state-history table was built now**, not deferred to when Phase 4 starts: `ApplicationStateEvent` (`application_state_events` - `application_id`, `from_state`, `to_state`, `source`, `created_at`). Phase 3's `queue()`/`mark_applied()` (`src/copilot/applications.py`) now append a row tagged `source="manual"` on every actual transition (a no-op call, e.g. `mark_applied` on an already-applied job, writes nothing - avoids duplicate identical rows). `Application.state` itself is unchanged; the history table is purely additive, created automatically by `Base.metadata.create_all` on the next `copilot init` (no data migration needed, matches the project's no-Alembic additive-schema convention).
**Why**: building the history table now, while Phase 3's write paths are the *only* writer to `Application.state`, means every transition from this point forward already has a `manual`-tagged record - no historical gap once Phase 4 adds its own `email:<event_id>`-tagged writes and needs to tell the two apart to implement D24's conflict rule. Deferring this to Phase 4 would have meant either backfilling history with a guess, or accepting a blind spot for any state set in between.

## D26: Phase 4 operating decisions - full email bodies stored locally, alerts only for invites/OAs, hourly sync (decided 2026-07-25, before the Phase 4 build)

**Chosen**: three user calls that shape how inbox monitoring behaves day to day.
1. **Full email bodies are stored** in `email_events` (and in `suggestions` for pending items), not just metadata + a snippet. The review surfaces (dashboard Suggestions tab, `copilot inbox review`) show complete evidence without a round-trip to Outlook, and future features (drafted replies - see the Phase 4 idea note in PLAN.md - or re-classification) can reuse the text without re-fetching. The bodies live only in the local, gitignored `copilot.db`, the same place the resume-derived data already lives; single-user local storage made this a comfort call, not a security one.
2. **Immediate alert emails fire only for interview invites and online assessments** - the two genuinely time-sensitive, action-required event types. Rejections, confirmations, and recruiter screens are information rather than deadlines; they surface in the daily digest's new "State changes" section instead. Rejected: alerting on every classified event (fastest awareness, but turns the alert channel into noise - and an alert channel that cries wolf gets ignored exactly when an OA deadline lands).
3. **Sync runs hourly** via launchd (`copilot schedule install`, `StartInterval` 3600). Bounds alert latency to under an hour while staying far below Graph API limits; launchd fires missed runs on wake (D8), so a closed laptop catches up rather than skipping.
**Why**: each of these is a preference with real trade-offs rather than a derivable answer (privacy comfort vs. convenience; interruption vs. awareness; freshness vs. background activity), so they were put to the user explicitly during the Phase 4 design discussion rather than assumed. Recording them here so the alert policy and cadence aren't re-guessed later - changing them is fine, but it should be a deliberate change, not drift.

## D27: Post-build refinements from a product-value review - daily-gated digest, thread continuity, auditable pre-filter, desktop notifications (decided 2026-07-25)

**Chosen**: four changes made after stepping back and asking "does this setup actually deliver value to the user?" once Phase 4 was code-complete but before live verification.
1. **The digest self-gates to daily even though the scheduled job is hourly.** The launchd job runs `inbox sync && digest --if-due` every hour; `--if-due` skips unless the last digest is 20+ hours old (20 rather than 24 so a run landing slightly earlier than yesterday's doesn't push the digest a whole day). Without the gate, any hour with a state change or new suggestion would send an email - the "daily digest" would silently degrade into hourly change notifications, contradicting D26's alert policy (only invites/OAs interrupt; everything else waits for *the daily* digest). Manual `copilot digest` never skips: asking for it is what makes it due.
2. **Thread continuity rescues pre-filter misses and strengthens correlation.** A recruiter's follow-up arrives as "Re: Next steps" from a personal corporate address - no ATS domain, no subject-pattern match - yet it belongs to a conversation already classified. A message whose `provider_thread_id` matches a stored email event now passes the pre-filter unconditionally and pre-correlates to that event's application (`matched_on="thread"`, checked before domain/name matching - it's the strongest signal there is). Also added: one suggestion per thread - a follow-up in a thread already awaiting review doesn't create a duplicate pending decision.
3. **Pre-filter skips are auditable.** A wrongly filtered message previously left no trace and was never reconsidered - the one failure mode the pipeline couldn't self-report. `inbox sync --dry-run` now lists every skipped sender/subject so the user can eyeball recall periodically; each spotted miss becomes a pattern to add.
4. **Alerts gained a macOS desktop notification channel.** An alert email about an interview invite is delivered to the same inbox that already contains the invite - low marginal value. The sync runs locally via launchd, so `osascript display notification` gives a genuinely different, immediate channel for free; the alert email stays as the durable fallback for when the user is away from the machine. Best-effort only: a broken notifier never fails the sync (and is a silent no-op off macOS, keeping a future non-Mac deployment safe).

**Rejected**: making the schedule itself daily (would bound alert latency at 24h, defeating D26's hourly-sync decision); a separate second launchd job for the digest (two plists to install/pause/explain, versus one flag); storing pre-filter skips in the DB (they're 95%+ newsletters - logging them as rows would be noise storage; a dry-run printout gives the audit without the residue); SMS/push services for alerts (external dependency and cost for a single-user local tool when the OS notifier is free).

**Why**: user asked for an honest product-value assessment of the email features before verifying them live. The review's conclusions: the sync's real value is keeping the tracker truthful without discipline, the digest's value depends on it staying daily and glanceable, alerts to the same inbox are the weakest link, and silent pre-filter misses are the one unauditable failure mode. All four changes follow directly from those conclusions; the user approved all four.

## D28: Backfill paths for missed email - intake folder, manual set-state, suggestion-to-job linking (decided 2026-07-25)

**Context**: the user asked what happens if an email the pipeline missed gets manually moved to a mailbox folder. Answer: nothing - folders were output-only, the watermark had already advanced past the message, and there was no manual way to record states beyond queued/applied or to hand a specific email to the pipeline. The system had no backfill path at all.

**Chosen**: three complementary escape hatches, all reusing the existing pipeline rather than adding new decision logic.
1. **Intake folder ("Career Copilot/Process")**: every sync also scans this subfolder. Anything the user drags there is processed regardless of age or pre-filter patterns - a human placing a message there IS the classification "this is job mail, look at it", so the filter doesn't get a veto (even a "not job related" model verdict flows on into a declinable suggestion rather than leaving the message stuck being re-classified every run). Everything downstream is unchanged: correlation, one Claude call, D20/D24 rules. Because the user now performs moves themselves - and Outlook regenerates a message's Graph id on every move - sync idempotency gained a second, move-stable key: the RFC 5322 `internetMessageId` header, stored on both `email_events` and `suggestions`. Old mail found via intake is recorded and filed but never fires an immediate alert (`ALERT_MAX_AGE` = 2 days): alerts exist to beat a clock, and an old invite's clock already ran. This also closes the "old recruiter emails from previous years" question from the watermark discussion - pre-watermark mail the user actually wants tracked now has a deliberate, per-message path in.
2. **`copilot jobs set-state <id> <state>`** (and a dropdown on the dashboard job page): manual override to any state in any direction, including backward - the undo mechanism for a wrong state, and the fallback when no email exists at all (a phone call, a missed message). Writes a `manual`-tagged history row like queue/mark-applied, so D24's conflict attribution keeps working.
3. **`copilot inbox confirm <id> --job <job_id>`** (and an optional "job #" field on the dashboard suggestion card): links an untracked-application suggestion to an already-tracked job instead of creating stub Company/Job/Application records. Needed because the correlator only sees subject/sender - an email whose company is named only in the body correlates to nothing, and plain confirm would have minted a duplicate application for a company already tracked. Linking follows the same D24 rules as automatic correlation: forward progress advances the application, anything else is recorded as history without touching state.
4. **`copilot jobs untrack <job_id>`** (and an Untrack button on the job's dashboard page, both behind a confirmation step - the first destructive action in the app): the undo for a wrong confirm or a mistaken queue/mark-applied, chosen as the one caveat worth closing immediately because it was the only mistake with *no* recovery path short of manual DB surgery - and the staged verification round deliberately creates fake tracked applications that need removing afterward. Deletes the application, its state history, and its email events; a job created from a confirmed email (`source="email"`) is deleted too, along with its company if nothing else references it, while discovery-found jobs revert to untracked listings. Suggestion rows are never deleted (their message ids are what keeps sync idempotent - no resurrection of the email that created the tracking); they're detached, and a pending conflict about the removed application is closed as declined since there's nothing left to decide.

**Rejected**: scanning the "Career Copilot" folder itself as intake (it holds Copilot-filed mail; a separate Process subfolder keeps "done" and "look at this" visibly distinct); auto-deleting or bouncing non-job mail dropped in intake by mistake (never destroy user mail - a declinable suggestion is the harmless failure mode); a free-form "reassign email to application" editor (confirm-time linking covers the real case without a new surface).

**Why**: the user's scenario - "an email was missed and I manually put it in a folder" - is the natural gesture; making that exact gesture work beats teaching a new command. All three additions keep the D1/D20/D24 posture: the human states facts (this is job mail; this state is true; this email belongs to job N) and Copilot does the bookkeeping, never the reverse.

## D29: The filed "Career Copilot" folder is also swept for unknown mail, reversing part of D28's rejection (decided 2026-07-25)

**Chosen**: every sync also scans the parent "Career Copilot" folder itself - not just the "Process" intake subfolder - and processes any message it has no record of, in place (no re-filing; it's already in the right folder). The scan is headers-only (`$select` without body): everything Copilot filed itself dedupes out on its move-stable Internet Message-ID without a body download or a Claude call, and only a stranger gets one extra fetch for its full body. Known mail costs one cheap paged listing per hour regardless of how large the folder grows.

**Rejected in D28, adopted now - what changed**: D28 kept the parent folder un-scanned to keep "done" (Career Copilot) and "look at this" (Process) visibly distinct. Discussing the "what if I move a filed email" scenario surfaced the flip side: "put it in the Copilot folder so Copilot sees it" is the natural wrong guess for the intake gesture, and its punishment was permanent silence - exactly the unauditable failure mode D28 set out to eliminate. The folders keep their distinct meanings (Process remains the explicit request lane and is documented as such); the parent scan is a forgiveness net, not a second front door. The dedupe-by-internet-id design (D28) is what made this free to adopt safely - without it, every Copilot-filed message would look new after its move-driven id change.

**Why**: a system should forgive a nearly-right gesture rather than punish it silently (user call after walking the scenario). Also closes the loop with untrack: a message dragged out of the folder and back in later is still recognized; an untracked-then-redropped one gets deliberately reprocessed, which is the behavior a user redoing something would expect.

## D30: Alert emails dropped after live testing; desktop notification is the only immediate channel (decided 2026-07-25)

**Chosen**: `send_event_alert` no longer sends an email - an interview invite / online assessment now triggers only the macOS desktop notification. The daily digest remains the durable, read-later record of every state change.

**Rejected**: keeping the alert email as a "durable fallback" (the D27 rationale). Live verification killed it: the user received the alert email sitting directly next to the interview invite it was alerting about, in the same inbox, and asked what value it added. None - if you're reading email you've already seen the original, and if you're not reading email the alert email doesn't reach you either. The fallback argument was circular. Also rejected: a config toggle to keep it optional - dead-value features shouldn't survive as configuration.

**Why**: this was flagged as the design's weakest link in the pre-verification product review (D27 "alerts deserve a better channel") and the user confirmed it within minutes of seeing it live. Removing it also drops the last non-digest use of Mail.Send, simplifying the alert path to a purely local, zero-cost action that can never fail a sync.

## D31: Conflicts and untracked suggestions share one three-way resolution; plus a batch of live-verification UX fixes (decided 2026-07-26)

Live verification (staged emails against the real Hotmail inbox) surfaced a cluster of real issues; this decision records the batch fixing them.

**1. A state conflict can be resolved three ways, not two.** D24 originally gave a conflict two outcomes: confirm (adopt the email's state) or decline (keep yours). Live testing of the multi-application-per-company case showed a third, common reality: the conflicting email is about a *different* application at the same company (you applied to two Syndigo roles; one was rejected, the other is now inviting you to interview). Neither adopting `interviewing` on the rejected application nor discarding the email is correct. So `confirm` now takes `job_id` (link to a different already-tracked application) and `as_new` (create a separate new application from the email) for conflicts too - in both cases the *flagged* application is left untouched, honoring D24's "never overwrite a human-set state" while still capturing the real event. The dashboard conflict card became a dropdown (adopt / create new / pick another application); the CLI gained `--new`. Same machinery as D28's untracked-suggestion linking, one branch wider.

**2. Conflict suggestions store the email's own extracted title, not the flagged job's.** Consequence of #1: if the user resolves as "new application", the new job must be built from what the email said. Storing the tracked job's title would make the new job's dedupe hash collide back onto the flagged application (this is exactly the `UNIQUE constraint failed: jobs.dedupe_hash` crash seen live before the fix). The "create new" path is also forward-only (`state_relation` guarded), so a dedupe collision can never silently overwrite an existing application's state.

**3. Dashboard double-submit no longer 500s.** FastAPI serves on a thread pool, so a double-clicked / re-POSTed Confirm ran two copies concurrently; both passed the check-before-insert dedupe and the loser crashed on the unique constraint. Fixed with a process-level lock serializing suggestion writes, an `AlreadyResolved` exception that turns a repeat action into a quiet redirect (not a 404/500), and buttons that disable on first click.

**4. Stale events never notify.** An email implying a state already reached (a duplicate ATS send, or - the live trigger - Copilot's own former alert email being re-ingested) is recorded but no longer fires a desktop notification. Old news is not actionable.

**5. Digest "new jobs" excludes email-created jobs.** Confirming an inbox suggestion creates a `Job` with `source="email"`; these were being counted as freshly *discovered* jobs in the digest ("2 new jobs" when nothing was discovered). They're applications the user already made and belong in the digest's "State changes" section, not the discovery count. `build_digest` now filters `source != "email"`.

**6. New "Applications" dashboard tab.** The Jobs tab answers "what should I apply to?"; a distinct pipeline view answers "where does everything I applied to stand?" - every tracked application, most-active-state first (interviewing/offer above applied/queued above terminal), with applied and last-activity dates. Requested during verification; no LLM, pure DB read.

**7. Jobs-tab UI fixes.** A tracked job's row now shows a state badge (queued/applied/interviewing/rejected, color-coded) instead of an "Apply" link - a job you're interviewing at shouldn't invite you to apply. The visa column no longer wraps mid-phrase (shorter labels + `nowrap`). The 50-row cap gained a "Show 50 more" link (the list was previously silently truncated with no way to page further).

**Why (the meta-point)**: none of these were visible in unit tests or design review - every one needed real emails flowing through the real mailbox to surface. This is the project convention ("verify end-to-end with real data") paying off: the conflict third-option, the dedupe crash, the self-ingested alert, and the digest miscount were all latent until exercised live.

## D32: The Integrations page is a control panel that edits API keys and the resume from the localhost UI (decided 2026-07-27)

The Integrations page is not just a read-only status board - it is the setup surface where the user connects services without leaving the browser: upload/replace the resume, set or update each API key (Anthropic, Adzuna, JSearch, Azure client id), and install/pause/resume the background schedule. Keys are written to `.env` (via python-dotenv's `set_key`, which preserves other lines and comments) **and** applied to `os.environ` in the running process, so a green status flips immediately with no dashboard restart.

**Editing secrets through the localhost UI is a deliberate reversal of an initial caution** ("never type secrets into a web form"). That caution is about hosted, multi-user, logged web apps; it does not apply here. This is a single-user tool bound to `127.0.0.1` with no auth (D4), and the project already treats local storage of sensitive data (resume-derived fields, full email bodies) as "a comfort call, not a security one" (D25). POST form bodies are not written to uvicorn's access log (only the URL is), inputs are `type=password` and never echoed back, and only a fixed allow-list of env keys can be written (`envfile.ALLOWED_ENV_KEYS`) so a crafted form can never set an arbitrary variable.

**Design: compact status rows, not detail cards.** A first attempt gave every integration an equal-weight card with a purpose line, a duplicate status line, and a large button - which read as clutter precisely in the common steady state (everything configured). Replaced with one calm row per item: a status dot (ready / needs-you / optional-off), the name, a terse status, and an inline action only where one exists; ready items recede and anything needing action stands out. The page answers one question at a glance - "am I fully connected, and if not what's the one next step?" - with a health summary line up top. Editors expand inline via native `<details>` (zero JavaScript, fully self-contained per D4's no-CDN constraint). The schedule (inbox-sync) controls moved here from Preferences so there is a single home for infrastructure/setup; Preferences stays focused on search and ranking.

**Rejected / deferred**: full in-UI email sign-in. The Microsoft Graph device-code flow (D-email) is interactive and long-polling - it prints a code the user enters at microsoft.com/devicelogin and blocks until they authenticate. Wiring that into a request cleanly needs background polling and progress UI; for now the row sets `AZURE_CLIENT_ID` and points to `copilot email login` in the terminal to finish. Also rejected: showing masked key fragments (last-4) - the green dot already conveys "set", and even a fragment is a needless local leak.

## D33: API usage page shows real quota only where a provider reports one - no fabricated numbers (decided 2026-07-27)

Built the dashboard's `/usage` page (the second Integrations-adjacent placeholder, docs/PLAN.md "Later/optional"'s `copilot apis status`) to the same compact-row visual language as D32's Integrations page, but read-only - no editors, no amber "needs you" state, since observability isn't a setup gate.

**Only JSearch gets a real "N of 200 left" number**, because it's the only integration that reports one: RapidAPI returns `x-ratelimit-requests-limit` / `-remaining` / `-reset` headers on every real search call. `discovery/jsearch.py` now captures those headers - read before `raise_for_status`, so a 429 quota-exhausted response still records `remaining: 0` - into `data/api_usage.json` via a new `api_usage.py` module, exactly as docs/PLAN.md originally specified: opportunistically, from calls already being made for real work, never a dedicated status-check call. The page just reads the last captured value.

**Every other API shows connection status and an honest text label, not a fake quota.** Anthropic is pay-as-you-go with no fixed quota; Adzuna and Microsoft Graph publish no rate limit; Greenhouse/Lever/Ashby, Remotive, RemoteOK, Nominatim, and USCIS are unauthenticated/courtesy-use with no key and no metering at all. Inventing a "quota remaining" figure for any of these would contradict the project's core "unknown stays unknown, never fabricated" stance (D10's salary/location precedent, applied here to infrastructure data). Grouped as **Metered** (needs a key, has *some* usage story) vs. **Free & unauthenticated** (always on, nothing to configure) rather than mirroring Integrations' Core/Optional, since neither of those axes maps to "may run out."

**Rejected**: extending this to full Anthropic cost/token tracking. That's pay-as-you-go with no quota to run out of, and instrumenting it would mean wrapping every Claude call site (scoring, tailoring, resume extraction, industry classification, dealbreaker compilation, title suggestions) - a distinct, larger feature with its own design questions (per-call vs. cumulative, session vs. all-time), better done as its own decision if the user wants cost visibility later.

## D34: Self-tracked Anthropic spend estimate - a new `llm.py` choke point, and no real "credits remaining" is possible (decided 2026-07-27)

The user asked whether the dashboard could show Anthropic credits/balance remaining. Checked the current Anthropic API docs directly rather than answering from memory: **there is no endpoint for this at all with a standard API key.** The only official facility is the Usage & Cost Admin API (`/v1/organizations/usage_report/messages`, `/v1/organizations/cost_report`), which (a) requires a separate **Admin API key** (`sk-ant-admin01-...`), a different and more privileged credential than `ANTHROPIC_API_KEY`, and (b) reports historical *spend* over a date range, not account *balance* or spending-limit headroom - that number is Console-only and not exposed via any API. So a literal "credits remaining" gauge is not buildable, full stop, regardless of engineering effort.

**What's actually buildable, and what got built**: a self-tracked estimate of what this tool's own Claude calls have cost, computed from token usage on real calls already being made - the same "capture opportunistically, never a dedicated check" principle as D33's JSearch quota. This reverses D33's explicit rejection of cost tracking, now that the user asked for it directly; D33 is left as the historical record of why it wasn't in scope yet.

**Centralized every Anthropic call site into a new `src/copilot/llm.py`** (`create`/`parse`, drop-in replacements for `client.messages.create`/`.parse`) rather than instrumenting six independent call sites individually. Before this, every one of `resume.py`, `industry.py`, `title_suggestions.py`, `rules.py`, `scoring/rubric.py`, and `email_agent/classifier.py` constructed its own `Anthropic()` client with no shared wrapper - a natural choke point that didn't exist yet. `llm.py` captures `response.usage` after every real call and persists a running per-month total (tokens + estimated USD, via a small static per-model price table) into `data/api_usage.json` alongside the JSearch quota data, best-effort (a malformed/mocked usage object never breaks the real call it's wrapping - same defensive pattern as D33's header capture). The Integrations/API-usage page's Anthropic row shows `~$X.XX est. this month (N calls)` when data exists, with the tooltip explicit that this is a self-tracked estimate from this tool's own calls, not the real account balance.

**Deliberately not a singleton client.** `get_client()` constructs a fresh `Anthropic()` on every call rather than caching one at module scope - matches the pre-refactor behavior exactly (every call site built fresh) and avoids a real test-isolation trap: a cached client built before a test patches `llm.Anthropic` would never see the patch, since `unittest.mock.patch` swaps the class, not any already-constructed instance.

**Pricing table is static and honest about its limits.** `_PRICING` covers `claude-sonnet-5` (at its introductory rate through 2026-08-31 - needs a manual bump to the standard rate after that, same maintenance pattern as `sponsorship.py`'s `FISCAL_YEAR`), `claude-opus-4-8`, and `claude-haiku-4-5`. A model not in the table means cost is `None` ("cost unknown"), never guessed - if a user changes `profile.yaml`'s `llm.model` to something unlisted, the month's total flips to "cost unknown for at least one model used" rather than silently under-reporting.

**Found and fixed a real test-isolation bug while verifying this live.** `data/api_usage.json` (a real, gitignored project file) was getting silently polluted by `pytest` runs: `tests/test_title_suggestions.py` mocks the Anthropic client with a `SimpleNamespace` response that has no `.usage` attribute at all, so `llm.create()`'s usage capture ran with `usage=None` and wrote real (zero-valued, but real) entries into the actual `data/api_usage.json` on every test run - 8 phantom call records confirmed live by isolating the test file and inspecting the file byte-for-byte. This wasn't a hypothetical: it had already happened to this project's own `data/` directory before being caught. Fixed at the root rather than patching the one test file: added an autouse `pytest` fixture (`tests/conftest.py`) that redirects both `api_usage.USAGE_PATH` and `envfile.ENV_PATH` (D32's key-writer, same class of risk) to a per-test tmp path for every test, so no test - this one, or any future one - can touch real project files just by exercising a code path that happens to hit one of these writers without deliberately opting in with an explicit `path=`.

## D35: Preferences redesigned around chip-based list inputs, with drag-reorder for ranked preferences (decided 2026-07-27)

The user called the Preferences page "terrible and unpolished" and asked for a redesign that makes configuring the job search "come naturally." Diagnosis went past surface polish: the page's three ranked-preference lists (location/industry/company preference) encode "most preferred first" purely as *line position inside a textarea* - the actual meaning of the field was invisible, something the user had to get right by careful typing rather than something they could see and arrange.

**Chosen: chip/tag inputs for every short list field, with a distinct drag-and-arrow-reorderable vertical layout specifically for the three ranked-preference fields** (offered as the recommended option against "polish the textareas but keep the pattern," which the user picked). Target titles and search locations (no order semantics - discovery queries all of them) render as a wrapping row of removable pills with a compact trailing "Add..." input. Location/industry/company preference render as a numbered vertical list where each row carries a drag handle *and* ▲▼ buttons (keyboard/no-drag-required reordering, not just mouse drag) plus its own remove button - order is now something you arrange, not something you infer. Dealbreakers stays a plain textarea: they're full sentences ("don't give me jobs based in Alabama"), which don't suit a pill shape.

**Zero backend changes - the hidden textarea is still the real form field.** Each chip field is progressive enhancement over a `<textarea class="chiplist-source" name="...">` that already holds the exact one-per-line value `dashboard.py`'s `_parse_lines()` has always parsed. `static/chiplist.js` (new, ~150 lines, no framework/dependency - consistent with this project's fully self-contained, no-CDN posture) hides that textarea and builds the chip UI in its place, syncing the textarea's `.value` to the newline-joined chip array on every add/remove/reorder. If JS fails to load, the plain textarea still renders and still works - this is the first page in the app that needs JS at all (Integrations' D32 deliberately stayed JS-free via `<details>`; Preferences' interaction - freeform add, remove, and *reorder* - doesn't fit that native-element trick, so this page takes the dependency instead of forcing an awkward native workaround).

**Two real bugs found and fixed during live verification, both CSS specificity/cascade traps, not JS logic bugs:**
1. The "Add..." input rendered as a giant box instead of a compact field - `.chiplist` is a `flex-direction: column` container, so a `flex-basis` on the input (an early attempt) was read as a *height*, not a width. Fixed by sizing the input with an explicit `width` instead of `flex-basis`.
2. Even with an explicit `width`, the input stayed full-width - Pico's own `input:not([type=checkbox],[type=radio]){width:100%}` rule has specificity (0,1,1) (an element selector plus a `:not()` argument), which beats a plain single-class selector like `.chiplist-input{width:...}` at (0,1,0) regardless of source order. Fixed by compounding the selector (`.chiplist .chiplist-input`) rather than reaching for `!important`.

## D36: USCIS H-1B refresh probes for a newer fiscal year instead of re-fetching a pinned one (decided 2026-07-27)

D18/`sponsorship.py` pinned `FISCAL_YEAR = 2023` as a module constant because FY2024/2025 both 404'd when last checked (2026-07-19). The user asked for the API usage page's "refresh manually" text to become a real button, and specifically that it "look if there is a more recent report and then use that as base" - a re-download of the same pinned year would satisfy the button but not the actual ask, since USCIS republishes at a new URL per fiscal year rather than updating one in place.

**Chosen: `current_cached_year()` reads the real year back from the cache filename** (`h1b_data_hub_fy{year}.csv`, globbed from `DATA_DIR`) instead of trusting the hardcoded constant, which now only serves as the fallback before anything's been downloaded. **`probe_newer_year()` checks candidate years newest-first via a streamed `GET`** (status code only, connection closed without reading the body - the real export can be tens of MB, so this avoids a wasted full download just to check reachability) and returns the newest one that's actually live, or `None`. **`refresh_h1b_data()`** combines both: adopts the newer year if one exists, otherwise re-verifies the current one is still the best available - either way it re-downloads with `force=True` and returns `(year, found_newer)` so the caller can report what happened. The CLI's `sponsorship-sync --refresh` and the dashboard's new `POST /usage/refresh-h1b` both call it and report the outcome in plain language ("Found and switched to FY2025 data" vs. "No newer report published yet"). `sync_sponsorship_data()`'s evidence string (`"N H1B petitions approved (FYxxxx)..."`) now takes an explicit `year` (falling back to parsing it from `cache_path`'s filename) instead of always stamping the module constant, so a company's stored evidence text stays accurate to whichever year actually produced it.

Verified live against the real USCIS endpoint (not mocked) - the refresh button correctly re-confirmed FY2023 as still the newest reachable year, matching D18's original finding eight days later.

## D37: Freeform autocomplete for Preferences chip fields, seeded from the jobs DB (decided 2026-07-27)

Following D35's chip redesign, the user asked for type-ahead suggestions on three fields: target titles ("type business, see business analyst / business developer"), search locations ("restrict to correct entries, maybe a dropdown of states"), and company preference ("free text but suggest as I type, since you now have the database with jobs"). Investigating each field surfaced a real constraint before designing anything: `locations` is passed straight through as Adzuna's `where` param / interpolated into JSearch's query text, and already accepts values like `"United States"` and `"Remote"` that aren't states at all - a *strict* state-only dropdown would make currently-valid values impossible to enter. Presented this as a design question rather than assuming; the user picked the option that keeps every field genuinely freeform, suggestions-only, confirmed via `AskUserQuestion`.

**Chosen: one generic autocomplete layered onto `chiplist.js` via `data-suggest="titles|locations|companies|industries"`**, never a restriction - Enter always commits whatever's typed, matched or not. A single `GET /api/suggestions` (new, `src/copilot/autocomplete.py`) is fetched once per page load and cached in a module-level promise, then filtered client-side per keystroke (single-user local tool, lists stay in the hundreds/low-thousands, no reason to round-trip per character). Data sources differ by field because their real data differs: **titles and companies merge a small static seed list with `DISTINCT` values already in the jobs DB** (real, market-relevant, grows with use - the seed exists only so the field isn't empty before much discovery has run); **locations is a static curated list only** (US states, "Remote", "United States", major metros as "City, ST") since a job's *stored* location is where it happened to post, not a place the user would search; **industries reuses the existing closed `Industry` enum** already shown as a hint string, at effectively no cost. Keyboard support (ArrowUp/Down to move a highlight, Enter to commit the highlighted match, Escape to dismiss) sits alongside the existing type-and-press-Enter flow rather than replacing it.

**One real bug found during live CDP + screenshot verification, a variant of the same Pico cascade trap D35 hit twice already:** suggestion text rendered as invisible white-on-white - the dropdown opened, sized correctly, and (confirmed via the CDP script reading `.textContent`) actually contained the right suggestions, but nothing was visible on screen. Root cause: Pico's own `button{...}` rule locally redefines the custom property `--pico-color` to its button-inverse (near-white) shade on every `<button>` element; `.chip-suggest-opt`'s own `color: var(--pico-color)` was specific enough to win the `color` property itself, but it was reading that same shadowed variable rather than the ambient page text color, so "winning the cascade" still resolved to white text. `.chip-remove` had already sidestepped this identical trap in D35 by using `color: inherit` instead of `var(--pico-color)` - applied the same fix here. Re-verified by screenshot after the fix: suggestion text renders legibly in all three fields (titles, industry, company).

**Follow-up correction (2026-07-28): companies didn't actually get a seed list at first, and it showed.** The paragraph above describes the intended design, but the initial implementation only gave `titles` a static seed - `companies` was DB-only. The user caught this live: typing "Meta" or "Microsoft" into company preference produced nothing, because neither had come up in a discovered job yet, and a company worth ranking is not the same set as a company that happens to already be in the DB. Added `SEED_COMPANIES` (~150 well-known employers grouped by the `Industry` vocabulary - big tech, banking, consulting, healthcare, retail, staffing, etc.) merged the same way titles already were. Companies suggested jumped from ~314 (DB-only, this user's real data) to 478 (merged) - verified live that Meta/Microsoft/Google/Amazon/Apple all resolve correctly post-fix.

**Verified with actual simulated user interaction, not just a screenshot.** No browser-automation library was in the project or available (`playwright`/`websockets` uninstalled); rather than accept a static render as "done," launched Chrome with `--remote-debugging-port` and drove it directly over the Chrome DevTools Protocol (`uv run --with websockets` - an ephemeral dependency, not added to the project) to simulate real keystrokes and clicks: typed a title and pressed Enter, clicked a chip's × to remove it, clicked a ranked item's ▼ to reorder, and Backspace-on-empty-input to remove the last chip - reading the hidden textarea's `.value` back after each action to confirm the sync actually happened, not just that the DOM looked right. All four passed against the live page with the user's real profile.yaml data.

## D38: Jobs table collapsed to a "role cell" to stop overflowing off-screen (decided 2026-07-28)

Screenshotting every dashboard page against real data (prompted by the user asking what else needed UI attention) surfaced two real defects on the Jobs page, the highest-traffic page in the app: the 8-column table (Fit, Title, Company, Location, Salary, Posted, Visa, Action) genuinely overflowed a normal laptop-width viewport - Visa and the Apply/state column got clipped off the right edge, not just a theoretical edge case - and the filter bar's bare `<button>Apply</button>` inherited Pico's `button[type=submit]{width:100%}` inside a `flex-wrap` bar, rendering as its own full-width primary-colored row (the same class of bug D35 already hit twice with `.chiplist-input` and `.chip-suggest-opt`, now a third confirmed instance - worth remembering as a standing rule for this codebase: **never leave a bare `<button>` unstyled inside a non-Pico layout**).

Presented two real trade-offs to the user rather than assuming: keep the flat 8-column table (smaller change, tighten widths + scroll affordance) vs. collapse Title+Company+Location into one block per row; and truncate long titles to a fixed 2 lines vs. let them wrap freely. **User picked the collapsed "role cell" and 2-line truncation for both** (`data-suggest`-style AskUserQuestion, matching this session's established pattern of confirming layout trade-offs before implementing).

**Chosen: `.role-cell`** - job title (bold, `-webkit-line-clamp: 2` to cap at two lines with an ellipsis, full title still in the anchor's `title=` attribute for hover and always shown in full on the job detail page - nothing is lost, just visually capped) with a `company · location` subtitle line beneath it (single-line `text-overflow: ellipsis`). **Verified live, not just by eyeballing a screenshot at one width.** Measured `.tablewrap`'s `scrollWidth` vs `clientWidth` via CDP across five viewport widths (1100-1440px) before and after the fix - the initial `.role-cell { max-width: 380px }` still overflowed at every width tested (content needs 937px, container caps at 863px regardless of viewport - shaving the role column, not widening the container, was the only real fix), narrowed to `290px` and re-measured clean (`overflowing: False` from 1200px up). Also found the real longest title in the actual jobs DB (128 characters, a multi-city posting) via a live DB query rather than a synthetic string, navigated to it, and confirmed the clamp truncates it to exactly two lines with a trailing ellipsis rather than blowing out the row height.

## D41: Jobs page gets manual discover/score triggers and seven new filters, all grounded in real DB coverage (decided 2026-07-28)

The user asked for a research pass on the Jobs page - specifically a manual search button and better filters - "so that it actually becomes more impactful." Investigating first (not just brainstorming) surfaced the real scope: `discover` and `score` were CLI-only (D11 deliberately kept them there), and the actual DB showed only 45 of 508 jobs scored (9%) - the dashboard had no way to close that gap at all. **Search and score deliberately stay separate**, per explicit user direction against the initially-recommended "chain them" design: discovery is free-ish (aside from JSearch's 200/month quota), scoring spends real Claude tokens, so the user controls when and how much to spend. **Bulk scoring is a dropdown (10/20/.../100 - the user's exact spec) + Score button**, not preset buttons or free-typed count. **One-off scoring lives both inline in the list** (compact button replacing "-" in the Fit column for unscored rows) **and on the job detail page** (per user: "maybe inline and then inside when you click on the job") - both routes share one `score_and_apply()` helper (new, `scoring/rubric.py`) with `copilot score`'s CLI command refactored to use the same function, so "scored" can't drift between the two surfaces (same reasoning as `ranking.py`'s single `rank_jobs()`).

**Filters: seven new fields, all following one rule already set by `min_fit`** (D12/D19) - a filter never hides a job just because a field is missing, only because the job is a confirmed non-match. Visa ("Likely sponsors" / "Hide explicit no-sponsor"), remote-only (mirrors `ranking.py`'s `_RemoteRule` OR-logic, not just the raw column), company/title text search, and salary floor (unknown salary always kept, per Preferences' own existing principle) all keep unknowns visible. **Industry and employment type are the deliberate exceptions** - picking one is an intentional categorical narrow: industry excludes unclassified companies (only 2/314, little lost); employment type excludes unlabeled jobs, found live to matter concretely - an early build that kept unknowns returned 110 jobs for "Contract" when only ~22 were actually labeled contract, which defeats the point of picking a specific type. **Two real bugs found only by testing live, not by review:**
1.
